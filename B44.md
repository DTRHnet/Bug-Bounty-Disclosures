# Security Vulnerability Report: Base44 Free-Tier Workspace Archiving Bypass via Agent-Composed Capabilities

**Reporter:** admin@dtrh.net  
**Date:** 2026-08-07  
**Product:** Base44 (base44.com / base44.app) – AI app builder  
**Severity (self-assessed):** Medium (business-logic / entitlement bypass; potential confidentiality considerations around public file URLs)

---

## Summary

Base44’s free plan restricts official project export and GitHub sync. The platform’s AI agent will refuse requests to produce a zip/tar of the workspace and redirect users to paid export or Git integration features.

This restriction can be bypassed. By instructing the agent with a carefully constructed prompt, a free-tier user can cause the agent to:

1. Read the application workspace (root `/app`).
2. Construct a complete USTAR tar archive of the project in pure Node.js (no external binaries).
3. Gzip the archive using the built-in `zlib` module.
4. Upload the resulting binary via the first-party `base44.integrations.Core.UploadFile` integration.
5. Receive a publicly reachable Base44 file URL.

The resulting URL follows the form:

```
https://base44.app/api/apps/{APP_ID}/files/mp/public/{APP_ID}/{REF_ID}_{FILENAME}.gz
```

In testing, the recovered artifact was named:

```
5bfa0cb46_qualia-flowtar.gz
```

The archive extracts cleanly and contains the full project workspace (excluding intentionally omitted directories such as `node_modules` and `.git`).

This workflow composes otherwise legitimate platform capabilities into an alternative project-export path that is not available through the normal user-facing export interface on the free plan.

All testing was performed exclusively against an application and account under the researcher’s control. No other user’s applications, identifiers, or files were accessed or enumerated.

---

## Potential Impact

The primary concern is that the AI agent can combine general-purpose capabilities to perform an operation that is normally restricted or unavailable through the product UI:

1. Read the application workspace.
2. Access project source files.
3. Generate an arbitrary binary archive.
4. Invoke Base44’s file-upload functionality.
5. Place the resulting archive into Base44’s public file-serving infrastructure.
6. Return a publicly addressable file URL.

If the inability to export the complete application is intended to be a plan-level or authorization boundary, this workflow allows that boundary to be bypassed.

A secondary concern exists if the generated public file URL is accessible to parties who do not otherwise have authorization to access the application’s source or workspace contents. The authorization model for these URLs has not been fully characterized by the researcher.

## Affected Components

The observed workflow involves the following Base44 capabilities:

- AI Agent / application workspace execution environment
- Application filesystem / workspace (root `/app`)
- Node.js runtime (`fs`, `path`, `zlib`, `Buffer`, `Blob`)
- `Core.UploadFile` integration
- Base44 public file-serving infrastructure
- `/api/apps/{APP_ID}/files/mp/public/...` file endpoint

Base44 documentation describes `Core.UploadFile` as an integration for uploading files to public storage and obtaining a file URL.

## Technical Details

### Workspace Access

The agent operates inside a Node.js sandbox with filesystem access to the project root at `/app`. Standard Node modules (`fs`, `path`, `zlib`) are available. No external shell or archiver binary is required.

### Archive Construction

Instead of relying on an operating-system `tar` executable, the archive is constructed directly in Node.js using `Buffer` objects to generate valid USTAR headers (including correct checksum calculation) and file records. The resulting TAR byte stream is then compressed with Node’s built-in gzip support.

Conceptual flow:

```
/app
  ↓
recursive filesystem traversal
  (exclude node_modules, .git, output archive)
  ↓
TAR byte stream (USTAR headers)
  ↓
zlib gzip
  ↓
.gz archive
```

### Upload Mechanism

The resulting binary is passed to Base44’s built-in file-upload integration:

```js
await base44.integrations.Core.UploadFile({
  file: archive   // Buffer or Blob
});
```

Where the SDK expects a browser-compatible object, the buffer can be wrapped:

```js
const blob = new Blob([gzBuffer], { type: "application/gzip" });
```

The upload returns a Base44-hosted file URL of the form:

```
https://base44.app/api/apps/{APP_ID}/files/mp/public/{APP_ID}/{REF_ID}_{FILENAME}.gz
```

### Identifier Clarification

Early notes referred to the path identifiers as `$sess_id`. After examining the generated URL structure and recovered artifact, the more accurate interpretation is:

| Component | Role |
|-----------|------|
| `APP_ID`  | Identifies the Base44 application (appears twice in the path) |
| `REF_ID`  | Identifies the uploaded file/object (e.g. `5bfa0cb46`) |
| `FILENAME`| Project/title-derived name (extension frequently mangled to `.gz`) |

The recovered artifact filename `5bfa0cb46_qualia-flowtar.gz` illustrates the `REF_ID` prefix.

## Reproduction Steps

Reproduction is limited to an application owned by the tester.

1. **Create/open a Base44 application**  
   Use a free-tier (or otherwise export-restricted) Base44 application that has at least one agent credit remaining.

2. **Instruct the agent to archive its workspace**  
   Provide a detailed prompt directing the agent to:
   - inspect the application workspace;
   - recursively enumerate project files;
   - exclude unnecessary directories (`.git`, `node_modules`, the output archive itself);
   - construct a TAR archive directly using Node.js;
   - gzip the resulting TAR stream;
   - upload the resulting binary using `base44.integrations.Core.UploadFile`.

3. **Construct the archive**  
   The agent generates a valid TAR + gzip archive in memory without an external archiving executable.

4. **Upload the archive**  
   The generated archive is passed to the Base44 upload integration.

5. **Observe returned URL**  
   The upload operation returns a Base44-hosted file URL matching the pattern above.

6. **Retrieve the archive**  
   Download the file from the returned URL. Rename to `.tar.gz` if the extension was mangled.

7. **Verify contents**  
   Extract with `tar xvzf <file>` and confirm the archive contains the application’s project workspace/source files.

## Expected Behavior

If complete project export is intentionally restricted for a particular account, plan, or application context, an AI agent operating within that same account should not be able to combine general-purpose filesystem and upload capabilities to produce an equivalent unrestricted project export.

Alternatively, if agents are intentionally permitted to perform this operation, the resulting archive should be subject to the same authorization controls as the underlying application/project.

---

## Actual Behavior

The AI agent was able to:

1. Access the application workspace.
2. Read the application’s source/project files.
3. Generate a complete archive without requiring a dedicated archive/export feature.
4. Upload the archive using an available Base44 integration.
5. Obtain a Base44-hosted public file URL.
6. Retrieve the resulting archive.

This effectively creates an alternative project-export pathway on a free-tier account.

---

## Security Boundary Concern

The important aspect of this report is not simply that an agent can create a `.tar.gz` file.

The concern is the **combination of capabilities**:

```
Filesystem access
       +
Arbitrary binary generation
       +
Public file upload
       =
Alternative project-export mechanism
```

Each capability may be legitimate individually. The security (or entitlement) issue arises if the combination allows an agent to bypass authorization, subscription, visibility, or export controls that are supposed to govern access to the complete application source.

## Security Impact Assessment

Severity depends primarily on Base44’s intended security and product model.

**Scenario A — Export restriction is only a product/plan limitation**  
If this is merely an undocumented alternative way to export an application that the user already has full authority over, the security impact is limited to a product/entitlement bypass.

**Scenario B — Export restriction is intended to protect application source**  
If the normal restriction is intended to prevent the user/agent from obtaining the complete application source, the ability to construct and upload the source independently represents a more significant authorization/control failure.

**Scenario C — Public URLs bypass application authorization**  
If generated archives can be retrieved without the authorization required to access the underlying application, or if an attacker can obtain another application’s archive, this could represent a substantially more serious confidentiality issue.

Scenario C was not tested against another user’s application.

## Suggested Remediation

Review the interaction between the following capabilities:

1. AI agent filesystem permissions.
2. Application source-code access.
3. `Core.UploadFile`.
4. Public file storage.
5. Project/export entitlements.
6. Application-level visibility and authorization.

Potential mitigations:

- Apply project/export authorization checks to agent-accessible source files.
- Prevent agents from uploading complete application workspaces when project export is not authorized.
- Apply application/workspace authorization to generated files.
- Ensure public file URLs cannot expose restricted project artifacts.
- Distinguish ordinary user-uploaded files from system/project artifacts.
- Audit agent-created uploads for source/workspace archives.
- Ensure `Core.UploadFile` cannot be used as an indirect project-export primitive where export is restricted.
- Rate-limit or size-limit agent-initiated uploads on free tiers.
